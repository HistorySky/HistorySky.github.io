重写 SchedulingConfigurer 动态配置定时任务

发表于： 2024-05-19
字数： 1516 阅读：≈ 4分钟 浏览：

进阶 Spring Boot：重写 SchedulingConfigurer 实现动态配置定时任务

在常规的 Spring Boot 开发中，我们习惯使用 @Scheduled 注解。但其 Cron 表达式通常硬编码在代码中，一旦执行周期需要调整，就必须修改代码并重启服务。为了实现“无需重启即刻生效”的任务管理，我们需要深入 SchedulingConfigurer 接口进行改造。

1. 核心避坑指南：消失的线程池 (NPE)

在重写 configureTasks 方法时，一个经典的错误是尝试通过 taskRegistrar.getScheduler() 获取现有的线程池。

为什么会出现空指针 (NPE)？

通过分析 ScheduledAnnotationBeanPostProcessor 类的 finishRegistration 源码可以发现其执行顺序如下：

  1. 调用 configureTasks：此时程序正在进行任务注册。

  2. 执行 afterPropertiesSet：在此方法内，taskRegistrar 才会真正去初始化并创建单线程或自定义线程池。

结论： 在 configureTasks 执行期间，线程池尚未创建。此时调用 getScheduler() 必定触发 NPE。

2. 实战代码：从数据库动态加载任务

下面的示例展示了如何从数据库或外部配置中心获取任务列表，并动态注册到 Spring 容器中。

@Override  
public void configureTasks(ScheduledTaskRegistrar taskRegistrar) {  
    // 1. 获取动态配置（脱敏处理：此处模拟从数据库读取任务配置列表）
    List<DynamicTaskConfig> configList = taskConfigService.getActiveTaskConfigs();  
  
    // 2. 循环创建并注册定时任务  
    for (DynamicTaskConfig config : configList) {  
        String cron = config.getCronExpression();  
        
        // Cron 合法性校验  
        if (StrUtil.isBlank(cron)) {  
            logger.warn("任务注册失败：Cron 表达式为空，任务 ID: [{}]", config.getTaskId());  
            continue;  
        }  
  
        // 3. 定义任务内容 (Runnable)  
        Runnable task = () -> {  
            // 执行通用业务逻辑
            businessProcessor.execute(config);  
        };  
  
        // 4. 设置执行周期 (Trigger)  
        // Trigger 的优势在于：每次任务触发时都会重新计算下一次执行时间，实现真正的动态化
        Trigger trigger = triggerContext -> {  
            return new CronTrigger(cron).nextExecutionTime(triggerContext);  
        };  
  
        // 5. 注册到注册器
        taskRegistrar.addTriggerTask(task, trigger);  
    }  
    
    logger.info("动态任务初始化完成，共注册 {} 个任务", taskRegistrar.getTriggerTaskList().size());  
}

3. 多种实现方式对比

方式 A：Lambda 表达式（推荐，简洁易读）

适用于逻辑简单的任务注册。

taskRegistrar.addTriggerTask(  
    () -> System.out.println("执行业务逻辑..."),  
    triggerContext -> {  
        String cron = "0 0 9-19 * * ?"; // 实际开发中建议从配置中心动态获取
        return new CronTrigger(cron).nextExecutionTime(triggerContext); 
    }
);

方式 B：普通匿名内部类

如果你需要在触发器内部处理更复杂的逻辑，这种写法结构更清晰。

Runnable task = new Runnable() {  
    @Override    
    public void run() {        
        // 执行业务代码
    }
};  

Trigger trigger = new Trigger() {  
    @Override    
    public Date nextExecutionTime(TriggerContext triggerContext) {        
        // 每次触发任务时，都会进入此方法重新获取 Cron
        String cron = fetchCronFromDb();  
        CronTrigger cronTrigger = new CronTrigger(cron);        
        return cronTrigger.nextExecutionTime(triggerContext);    
    }
};  

taskRegistrar.addTriggerTask(task, trigger);

4. 进阶：如何实现 Cron 的实时修改？

很多同学会问：“我已经把任务注册进去了，如果数据库里的 Cron 变了，代码需要重新运行吗？”

答案是：取决于你如何实现 Trigger。

方案一：自动感知（推荐）

在 Trigger 的 nextExecutionTime 方法中，我们不应该传入一个写死的字符串，而应该传入一个获取逻辑。因为这个方法在每次任务执行结束、计算下一次执行时间时都会被调用。

// 在注册任务时，传入获取 Cron 的逻辑
taskRegistrar.addTriggerTask(
    () -> businessProcessor.execute(config), 
    triggerContext -> {
        // 关键点：每次任务触发时，都重新去配置中心或数据库查询一次最新的 Cron
        String latestCron = taskConfigService.getCronByTaskId(config.getTaskId()); 
        
        // 重新构建 CronTrigger，计算下一次执行时间
        CronTrigger cronTrigger = new CronTrigger(latestCron);
        return cronTrigger.nextExecutionTime(triggerContext);
    }
);

优点： 极其简单，只要数据库记录一变，下一次任务就会按新周期执行。 缺点： 仅能在任务完成后的空档期更新。如果你的任务是一年执行一次，你现在想改成一分钟一次，那么它必须等今年这次跑完才能感知到变化。

方案二：手动重置（彻底刷新）

如果你需要修改后“立即生效”，不考虑当前任务的间歇，那么你需要持有 ScheduledTaskRegistrar 的引用，并进行以下操作：

  1. 维护一个本地 Map<TaskId, ScheduledTask> 记录已注册的任务。

  2. 当修改发生时，通过 ScheduledTask.cancel() 停止旧任务。

  3. 再次调用 taskRegistrar.addTriggerTask(...) 注册新任务。

5. 总结与建议

  1. 谨慎对待 NPE：记住 configureTasks 执行时 taskRegistrar 的线程池还没准备好。

  2. 性能考虑：如果动态任务数量巨大，建议手动在 configureTasks 中初始化并设置一个 ThreadPoolTaskScheduler 实例，避免单线程阻塞。

  3. 动态性说明：通过 Trigger 接口注册的任务，其 Cron 表达式可以在每次执行完后重新查询，从而实现不重启服务直接修改执行周期的效果。

  4. 通过 Trigger 接口的动态计算特性，我们实现了**“配置驱动调度”**。这意味着你的 Java 代码成了纯粹的执行引擎，而调度的灵魂（Cron）完全交给了数据库或 Nacos 等配置中心。
