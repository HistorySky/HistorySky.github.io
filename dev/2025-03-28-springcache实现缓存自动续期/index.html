Spring Cache实现 API Token 自动续期

发表于： 2025-03-11
字数： 1108 阅读：≈ 3分钟 浏览：

实战：利用 Spring Cache 巧妙实现 API Token 自动续期缓存

在对接第三方平台 API 时，Token 管理通常是最烦琐的一环：Token 有效期短、获取频率受限。如果每次请求都实时获取，不仅浪费带宽，还容易触发对方的频率限制。

虽然 Spring Cache 提供了 @Cacheable 等注解，但在处理 “逻辑过期” 或 “双 Token 自动续期” 场景时，编程式缓存（Manual Caching）往往更加灵活。本文将带你实现一个健壮的 Token 缓存方案。

1. 环境准备：配置 Spring Cache

首先，在 Spring Boot 项目中开启缓存支持。为了演示方便，我们使用 Spring 自带的 simple 类型（基于 ConcurrentHashMap），实际生产环境可无缝切换为 Redis。

YAML 配置 

spring:
  cache:
    type: simple # 开启 Spring Cache 简单内存缓存模式

开启注解

在启动类或配置类上增加 @EnableCaching 注解：

@Configuration
@EnableCaching
public class CacheConfig {
    // 注入自定义缓存管理器配置（可选）
}

2. 核心逻辑：双重校验与自动续期

在业务场景中，我们通常面临两个时间戳：

  1. RequestToken 过期时间：用于业务请求。

  2. RefreshToken 过期时间：用于在 RequestToken 过期后，刷新获取新的 Token 组合。

以下是完整的编程式缓存实现示例：

@Slf4j
@Service
public class TokenService {

    @Autowired
    private CacheManager cacheManager;

    private static final String CACHE_NAME = "API_TOKEN_CACHE";
    private static final String CACHE_KEY = "CURRENT_REMOTE_TOKEN";

    /**
     * 获取有效的请求 Token
     */
    public String getSafeToken() {
        // 1. 从缓存管理器中获取指定的 Cache 对象
        Cache cache = cacheManager.getCache(CACHE_NAME);
        if (cache == null) return null;

        // 2. 获取缓存包装器对象
        Cache.ValueWrapper valueWrapper = cache.get(CACHE_KEY);
        TokenDataDTO tokenData;

        // 场景 A：缓存完全为空 -> 强制初始化
        if (valueWrapper == null || valueWrapper.get() == null) {
            return refreshAndSaveToken(cache, "INITIAL_SECRET", false);
        }

        tokenData = (TokenDataDTO) valueWrapper.get();

        // 场景 B：RequestToken 未过期 -> 直接返回
        if (!this.isExpired(tokenData.getRequestExpiryTime())) {
            log.info("Token 仍在有效期内，直接返回");
            return tokenData.getRequestToken();
        }

        // 场景 C：RequestToken 已过期，检查 RefreshToken 是否也过期
        if (this.isExpired(tokenData.getRefreshExpiryTime())) {
            // RefreshToken 也挂了，只能用初始密钥重新“大刷新”
            log.info("所有密钥均已过期，执行完全刷新");
            return refreshAndSaveToken(cache, "INITIAL_SECRET", false);
        } else {
            // RefreshToken 还没过，通过它换取新的 RequestToken
            log.info("RequestToken 过期，通过 RefreshToken 换取新令牌");
            return refreshAndSaveToken(cache, tokenData.getRefreshToken(), true);
        }
    }

    /**
     * 调用远程 API 刷新并存入缓存
     */
    private String refreshAndSaveToken(Cache cache, String secret, boolean isRefreshStep) {
        // 脱敏处理：模拟远程 API 调用
        TokenDataDTO newToken = remoteApiAdaptor.fetchToken(secret, isRefreshStep);
        
        // 更新缓存
        cache.put(CACHE_KEY, newToken);
        
        log.info("Token 已更新, 下次过期时间: {}", newToken.getRequestExpiryTime());
        return newToken.getRequestToken();
    }

    private boolean isExpired(Long expiryTime) {
        return expiryTime == null || System.currentTimeMillis() > expiryTime;
    }
}

3. DTO 结构封装 

@Data
@AllArgsConstructor
@NoArgsConstructor
public class TokenDataDTO implements Serializable {
    private String requestToken;      // 用于业务请求的 Token
    private Long requestExpiryTime;   // RequestToken 到期时间戳
    private String refreshToken;     // 用于刷新的 Token
    private Long refreshExpiryTime;  // RefreshToken 到期时间戳
}

4 为什么不直接用 @Cacheable？

虽然 @Cacheable 很方便，但在 Token 场景下有局限性：

  • 无法动态感知过期：@Cacheable 默认只要缓存有值就返回，除非到了 TTL 强制清理。而 Token 需要根据返回体里的 expiryTime 字段进行逻辑判断。

  • 多状态维护：我们需要同时维护两个过期时间，手动操作 CacheManager 能实现更细粒度的控制。

5. 总结

通过 Spring Cache 的 CacheManager 结合编程式逻辑，我们实现了一套具备自愈能力的缓存机制：

  1. 高性能：内存级读取，毫秒响应。

  2. 低耦合：业务方只需调用 getSafeToken()，无需关心内部是如何刷新的。

  3. 高可靠：通过双 Token 机制，极大降低了业务请求因 Token 失效而中断的概率。
