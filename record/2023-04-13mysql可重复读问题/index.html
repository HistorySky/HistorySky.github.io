深入理解 MySQL 可重复读(REPEATABLE READ)隔离级别

🔍 事务隔离级别基础

在数据库系统中，事务隔离级别决定了多个并发事务如何相互影响。MySQL 提供了四种标准隔离级别：

隔离级别脏读不可重复读幻读
READ UNCOMMITTED可能可能可能
READ COMMITTED避免可能可能
REPEATABLE READ避免避免可能
SERIALIZABLE避免避免避免

🎯 REPEATABLE READ 核心特性

MySQL 默认的事务隔离级别是可重复读(REPEATABLE READ)，它具有以下关键特性：

1. 一致性视图机制

  • 在事务开始时创建数据快照
  • 整个事务期间都使用这个一致的视图
  • 保证多次读取相同数据结果一致

2. 解决不可重复读问题 

-- 事务A
START TRANSACTION;
SELECT balance FROM accounts WHERE id = 1; -- 返回 1000

                        -- 事务B更新数据
                        UPDATE accounts SET balance = 900 WHERE id = 1;

SELECT balance FROM accounts WHERE id = 1; -- 仍然返回 1000
COMMIT;

3. 幻读处理 

-- 事务A
START TRANSACTION;
SELECT * FROM users WHERE age > 30; -- 返回 2 条记录

                        -- 事务B插入新数据
                        INSERT INTO users(name, age) VALUES ('Mike', 35);

SELECT * FROM users WHERE age > 30; -- 仍然返回 2 条记录
COMMIT;

⚙️ 查看和设置隔离级别

查看当前隔离级别 

-- 传统查看方式
SHOW VARIABLES LIKE 'tx_isolation';

-- MySQL 8.0+ 推荐方式
SHOW VARIABLES LIKE 'transaction_isolation';

设置全局隔离级别 

SET GLOBAL TRANSACTION ISOLATION LEVEL REPEATABLE READ;

设置会话级隔离级别 

SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;

💻 Spring Boot 中的配置实践

方法级事务配置 

@Service
public class AccountService {

    @Transactional(
        isolation = Isolation.REPEATABLE_READ,  // 隔离级别
        propagation = Propagation.REQUIRED,      // 传播行为
        timeout = 30,                            // 超时时间(秒)
        rollbackFor = Exception.class            // 回滚异常
    )
    public void transferFunds(Long fromId, Long toId, BigDecimal amount) {
        // 转账业务逻辑
    }
}

全局事务配置 

@Configuration
@EnableTransactionManagement
public class TransactionConfig {

    @Bean
    public PlatformTransactionManager transactionManager(DataSource dataSource) {
        return new DataSourceTransactionManager(dataSource);
    }
    
    @Bean
    public TransactionTemplate transactionTemplate(PlatformTransactionManager manager) {
        TransactionTemplate template = new TransactionTemplate(manager);
        template.setIsolationLevel(TransactionDefinition.ISOLATION_REPEATABLE_READ);
        template.setPropagationBehavior(TransactionDefinition.PROPAGATION_REQUIRED);
        return template;
    }
}

⚠️ 使用注意事项

MVCC 机制限制

  • 读操作使用快照数据
  • 写操作使用当前最新数据
  • 可能导致"写入倾斜"问题

锁升级场景

当执行以下操作时，可重复读会升级为记录锁：

SELECT ... FOR UPDATE
SELECT ... LOCK IN SHARE MODE
INSERT INTO ... SELECT ...

死锁风险 

-- 事务A
START TRANSACTION;
SELECT * FROM accounts WHERE id = 1 FOR UPDATE;

                        -- 事务B
                        START TRANSACTION;
                        SELECT * FROM accounts WHERE id = 2 FOR UPDATE;

-- 事务A尝试锁定id=2
SELECT * FROM accounts WHERE id = 2 FOR UPDATE; -- 阻塞

                        -- 事务B尝试锁定id=1
                        SELECT * FROM accounts WHERE id = 1 FOR UPDATE; -- 死锁发生

📊 性能优化建议

  1. 合理控制事务粒度

    • 避免长事务占用资源
    • 拆分大事务为多个小事务

  2. 索引优化

    -- 添加合适索引减少锁定范围
CREATE INDEX idx_account_user ON accounts(user_id);

  3. 监控长事务

    -- 查看运行时间超过60秒的事务
SELECT * FROM information_schema.INNODB_TRX 
WHERE TIME_TO_SEC(TIMEDIFF(NOW(), trx_started)) > 60;

🌟 最佳实践场景

  1. 财务系统：确保账户余额查询一致性
  2. 报表生成：保证统计期间数据不变
  3. 库存管理：防止超卖现象

经验总结：REPEATABLE READ 在提供数据一致性的同时，需要开发者理解其底层机制和潜在陷阱。合理配置隔离级别并配合良好的索引设计，可以在保证数据一致性的同时获得最佳性能。
